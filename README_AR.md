# AL-BARQ — متجر إلكتروني جديد

هذا مشروع تأسيسي جديد مستقل عن أي نسخة قديمة. يتضمن واجهة React/TypeScript، تحميل المنتجات من Supabase، سلة محلية، نموذج إتمام الطلب، ومخططًا أوليًا آمنًا لإنشاء الطلبات عبر Edge Function ومعاملة SQL.

> **حالة المشروع:** نقطة بداية تنفيذية وليست إعلانًا بأن التكامل قد اختُبر على مشروع Supabase فعلي. يلزم إعداد البيئة وتطبيق SQL ونشر Edge Function وإنشاء مسؤول ثم تنفيذ الاختبارات قبل الاستخدام العام.

## التقنيات ولماذا
- React + TypeScript + Vite: واجهة مكونة وقابلة للصيانة، وفحص أنواع أثناء البناء.
- Supabase/PostgreSQL: منتجات وطلبات ومصادقة وسياسات RLS.
- Supabase Edge Functions: التحقق الخادمي وعدم كشف مفتاح الخدمة في المتصفح.
- Vitest: اختبارات آلية لمنطق المساعدة.

## 1. المتطلبات
- Node.js إصدار LTS حديث وnpm.
- حساب Supabase جديد لهذا المشروع.
- Supabase CLI لنشر Edge Function (اختياري محليًا، مطلوب للنشر بالطريقة الموثقة).

## 2. التشغيل المحلي
1. فك ضغط المشروع وافتح المجلد في الطرفية.
2. شغّل `npm install`.
3. انسخ `.env.example` إلى `.env.local`.
4. ضع عنوان مشروع Supabase ومفتاح `anon`/publishable العام فقط في `.env.local`.
5. شغّل `npm run dev`.

لا تضع `service_role` أو أي سر في `VITE_*` أو في ملفات الواجهة أو Git.

## 3. قاعدة بيانات Supabase
1. أنشئ مشروع Supabase جديدًا ولا تستخدم مشروع المتجر القديم في هذه المرحلة.
2. افتح SQL Editor.
3. راجع ثم نفّذ `supabase/migrations/0001_initial_schema.sql` مرة واحدة.
4. تأكد أن RLS مفعّل على جميع الجداول. لا تضف سياسة عامة تسمح للجميع بالقراءة أو الكتابة على الطلبات.

### إنشاء أول مسؤول
1. أنشئ مستخدمًا من Supabase Dashboard → Authentication → Users.
2. انسخ UUID الخاص به.
3. في SQL Editor نفّذ: `insert into public.admin_users(user_id) values ('UUID-هنا');`
4. لا تتيح للعميل إدخال نفسه في `admin_users`. إدارة العضوية تتم يدويًا من بيئة موثوقة فقط.

لوحة الإدارة نفسها لم تُنفّذ بعد في هذه المرحلة؛ سيُضاف مسار الإدارة وواجهاته وسياساته في مرحلة منفصلة.

## 4. إعداد ونشر Edge Function
تحتاج الوظيفة إلى أسرار بيئة الخادم `SUPABASE_URL` و`SUPABASE_SERVICE_ROLE_KEY` التي يوفرها Supabase في بيئة Edge Function. لا تنسخ المفتاح إلى الواجهة أو ترسله في المحادثة.

باستخدام Supabase CLI بعد ربط مشروعك الجديد:
```bash
supabase login
supabase link --project-ref YOUR_PROJECT_REF
supabase functions deploy create-order
```

اضبط `ALLOWED_ORIGIN` على أصل موقعك المنشور بدل `*` قبل الإطلاق، وتأكد من إعداد CORS بحسب نطاقاتك. راجع سجلات الوظيفة بعد النشر. لا تختبر بيانات عميل حقيقية قبل ضبط سياسات الوصول.

## 5. الاختبارات
```bash
npm test
npm run build
```

هذه الاختبارات الأولية تغطي مساعدات تنسيق العملة فقط. يجب تنفيذ اختبارات تكامل فعلية على مشروع Supabase تجريبي للتحقق من حفظ `orders` و`order_items`، المخزون، idempotency، rate limit، RLS، ودخول المسؤول. لا تعتبر النجاح محققًا قبل تشغيل هذه الاختبارات في بيئتك.

## 6. ملاحظات أمان مهمة
- الواجهة ترسل معرفات المنتجات والكميات فقط؛ لا تعتمد على الأسعار المرسلة من المتصفح.
- دالة SQL `create_order_transaction` تعيد قراءة الأسعار وتتحقق من المخزون وتكتب الطلب وتفاصيله وتخصم المخزون ضمن معاملة واحدة.
- يوجد مفتاح idempotency فريد لمنع إعادة إنشاء الطلب بالمفتاح نفسه. يجب أن يعيد العميل استخدام المفتاح نفسه عند إعادة محاولة نفس العملية؛ الواجهة الحالية تولّد مفتاحًا جديدًا عند كل إرسال، لذا يلزم تحسين إدارة إعادة المحاولة قبل الإطلاق العام.
- محدد المعدل الحالي يستخدم نافذة ثابتة 10 دقائق بحد 8 طلبات لكل hash عنوان IP. تحقق من رأس عنوان IP الموثوق في بيئة النشر لديك؛ لا تثق برأس يمكن للعميل تزويره. يمكن أن تختلف الرؤوس المتاحة حسب المنصة.
- إعداد `ALLOWED_ORIGIN` يحتاج إلى أصل الموقع الحقيقي. لا يُعد `*` إعداد إطلاق موصى به.
- صفحة إدارة المنتجات والطلبات لم تكتمل في هذه المرحلة.
- لم يُختبر الاتصال الفعلي بمشروع Supabase في بيئة هذا التسليم؛ لا تُدخل بيانات اتصال حقيقية إلا في `.env.local` وبيئة الخادم.

## 7. مراحل التنفيذ المتبقية
1. تشغيل الواجهة والتحقق من البناء.
2. ربط مشروع Supabase جديد وتطبيق migration.
3. إضافة منتجات فعلية من لوحة Supabase أو لوحة الإدارة التي ستُبنى لاحقًا.
4. اختبار Edge Function والطلب والمخزون ومنع التكرار.
5. بناء لوحة الإدارة ومصادقتها واختبار RLS.
6. اختبارات أمنية وتجاوبية ثم النشر.
